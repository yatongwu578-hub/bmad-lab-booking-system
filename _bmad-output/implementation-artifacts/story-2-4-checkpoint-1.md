## 实施设计

1. **入口。** 「我的预约」列表与本人详情把待审核、已批准标为可进入验证的候选，提示只有开始前可取消，页面不是授权或时钟依据。新增 `/reservations/<pk>/cancel/`（`reservation-cancel`）。GET 使用独立的本人范围只读投影显示编号、设备、北京时间及当前预约状态，终态不显示提交按钮。GET 不调用会触发 FR-018 的原详情服务，不加设备锁或写业务。页面有明确的确认按钮和「不取消，返回详情／我的预约」。原 201、列表、详情及管理员路由行为不变。
2. **请求闸口。** POST 使用 Django 会话和 CSRF，目标以 URL 主键与服务端角色和当前账号归属确定。不接受客户端归属、角色、设备、状态或时间覆盖。无业务输入的表单仅携带 CSRF，拒绝结果会影响范围或语义的未知输入，非法方法或格式先于取消服务拒绝。服务先查活动师生账号，再用 `pk + applicant_id` 定位设备，不存在与他人目标用同一 404。管理员不因 staff/superuser 标记获得师生业务权限。匿名沿用登录跳转。直接访问、浏览器回退、重复 POST 都不能绕过服务端保护。
3. **短事务。** 使用 `_durable_operation`、`lock_equipment`、`_recheck_applicant`。先锁目标设备行，复核账号并按原预约、归属、设备重新读取，不锁预约在前、不扩大失效范围。授权丢失时无取时、投影或业务写入。目标存在且授权有效后独立调用一次 `_decision_time`，同一值用于边界、FR-018 和历史；不读其他设备或待审记录作取消收尾。设备当前维修／停用不改变取消条件。不新增占用表，原预约状态变化自然退出有效占用集合。已开始的时段不会因释放而变成合法新申请。
4. **持久性和反馈。** 成功时只更新预约 `status`，用现有审计模型加一条 `action=cancel`、`actor_type=applicant`、真实 `actor_id`、单预约外键、原／新状态和锁后 `decision_at`，`recorded_at=Now()`，理由留空。到期待审只复用 `_expire` 写既定系统历史，正常提交后再返回业务拒绝。提交后渲染结果，不通过隐式 GET 重新调用有副作用的查询。成功反馈 200，已开始／终态／已失效业务拒绝 409，确认数据库失败与提交未知分别 503 且文案区分；不把数据库异常称作冲突。未知不声称状态、没有重试按钮或自动跳转。合法用户可以主动返回列表查询；缺失／异主结果不含对象详情或对象链接。列表、详情与取消页延续模板自动转义、无缓存行为。

## T-01／T-02／T-04 · 时序组

独立 PostgreSQL 连接、受控屏障、`pg_blocking_pids` 或协议内等锁证据，记录各 PID、目标、实际时间戳和真实顺序。保留 `设备锁 → 权限复核 → 锁后重读 → 唯一 clock_timestamp() → 写入 → COMMIT` 的参数化证据。模拟时钟只作精确边界，真实跨界用数据库短窗口，不改系统时钟、不等待整点。批准状态只由测试夹具建立。

| 时序编号 | 操作顺序 | 必验结果 |
| --- | --- | --- |
| I01／I02 | 开始前取消先提交／新申请先判定，同设备同一合法未来时段 | 取消先时新申请 201，原单保留为取消且只剩新的一条有效占用。申请先时明确冲突，随后取消释放，不追改 409、不重试。 |
| I03 | 两个合法取消请求竞争同一预约；另测提交后顺序重发 | 一次成功、一次业务拒绝、只有一条取消历史，后发按锁后终态，无残留占用。 |
| I04／I05 | 取消与 2.2 占用查询、2.3 本人列表／详情依次各测两种持锁先后，取仍在开始前的待审夹具；本人列表加逆序的第二设备候选 | 查询先只反映提交前已授权占用／状态，后续查询才见取消；取消先时等待中的查询重读，不返回已释放占用或再写历史。多设备列表仍按设备主键升序，新取消仅锁目标设备。对批准或终态的无锁查询不伪称观察到设备锁等待。 |
| I06／I07 | 上述查询先获得设备锁并使待审失效／取消先触发 FR-018 后查询并重复取消 | 最终一条系统失效历史，零取消历史、无有效占用。已批准对照到点保持批准，不从活动窗口误剔。锁后权限收回用下组独立探针。 |
