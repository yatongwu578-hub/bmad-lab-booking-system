# Epic 1 Context: 安全访问与可信设备目录

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

学生、教师和实验室管理员通过预置账号以明确的身份访问设备目录。管理员可以建立和维护具体设备的档案，使师生能按唯一编号识别实物并了解设备当前状态，为后续查询占用和提交预约提供可信的设备数据。

## Stories

- Story 1.1: 使用预置账号登录并获得明确业务身份
- Story 1.2: 管理员新增具体设备基础档案
- Story 1.3: 查看设备目录与具体设备详情
- Story 1.4: 管理员维护设备基础信息并保护设备身份

## Requirements & Constraints

- 预置账号各有一个必填业务角色。登录依赖有效凭据和服务端会话。每个受保护入口均检查身份及该操作所需的权限。学生、教师和管理员均可读取设备目录，设备新增和基础信息维护仅向业务管理员开放。
- 目录和详情按具体设备展示编号、名称、类别、位置、说明和当前状态。设备编号创建时唯一，后续业务操作保持原编号及对象关联。新设备初始状态为可用，基础信息维护须保留当前状态，无物理删除入口。
- 对本 Epic 已实现入口逐项记录未授权拒绝、无受限内容泄露、无业务数据变化三项结果，以实际用例数为分母，目标为 100%。合法访问和操作作为独立对照。全项目权限矩阵随新增入口继续验证，预约竞争另有验收。

## Technical Decisions

- 采用本机 Windows、Python 3.13、Django 5.2 LTS、psycopg 3 和 PostgreSQL 17.x，以 venv、Django 模板和模块化单体运行。本机已批准使用独立的 PostgreSQL 17.12 实例和环回端口 5433。运行、迁移和集成测试使用对应的数据库及权限，数据库配置缺失时明确报错。使用北京时间业务配置和带时区的时间点保存。
- 账号继承 Django 的 `AbstractUser`，首次迁移前指定 `accounts.User`。角色由服务器从账号读取，持久化取值限于 `student`、`teacher`、`admin`，由应用校验和数据库约束共同保障。使用 Django 认证、密码哈希、会话和 CSRF 防护。权限以业务角色为准。预置操作接受受保护的输入，已有同角色账号保持原样，角色冲突回滚本批。
- 业务操作通过专用页面及服务校验权限，无自助注册或 Django Admin 入口。设备编号的唯一性由数据库保障。基础信息编辑在短事务内取得设备锁并重新读取，防止旧表单覆盖设备状态。普通目录读取无需写锁或按需失效。设备与业务关联应保留，数据库约束和实际事务行为在独立的真实 PostgreSQL 测试库验证。

## UX & Interaction Patterns

- 为学生、教师和管理员提供共同的登录入口。受保护页面显示当前账号和业务身份。无效登录给出反馈，匿名会话无法取得受保护信息。
- 目录清楚区分设备的可用、维修和停用状态，提供空目录和对象不存在的反馈。设备当前状态表示设备情况，指定日期的占用和最终预约结果由后续预约入口呈现。

## Cross-Story Dependencies

- 1.1 无前置 Story。1.2 依赖 1.1 的身份和权限基础。1.3 依赖 1.1 和 1.2。1.4 复用 1.1 至 1.3 的授权、设备档案和查询。
- Epic 2 复用本 Epic 的身份、权限与设备档案，新增预约能力时验证设备关联。Epic 3 复用设备档案和既有预约服务实现状态转换及受影响预约处置。本 Epic 的账号和设备目录可独立交付。
