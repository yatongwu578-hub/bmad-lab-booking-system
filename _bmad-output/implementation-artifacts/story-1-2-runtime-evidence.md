## 实际授权

执行 PostgreSQL 17 `psql.exe -X -w -h 127.0.0.1 -p 5433 -U lab_booking_migrator -d lab_booking -v ON_ERROR_STOP=1 --single-transaction -f -`。同一事务先核对实际目标、角色、迁移和 owner、identity 及现有权限，再执行唯一 GRANT，并检查有效权限。输出 `DO / GRANT / DO`，退出 0。

```sql
GRANT INSERT (number, name, category, location, description, status), SELECT (id)
ON TABLE public.equipment_equipment TO lab_booking_app;
```

实际有效权限为六列 INSERT、仅 `id` 可 SELECT。无设备表整表授权、无其他列读权限、无设备 UPDATE、DELETE、TRUNCATE、REFERENCES、TRIGGER 或 MAINTAIN。未增加 schema CREATE、序列访问或角色权限。原有 schema USAGE 和 Story 1.1 权限继续使用。运行时成功新增验证了当前 identity 默认值和 `RETURNING id` 路径可用。

## 本机正常启动

在仓库根目录使用普通 PowerShell，沿用原 `.venv`。

```powershell
$python = '.\.venv\Scripts\python.exe'
$env:LAB_BOOKING_DB_MODE = 'runtime'
$env:PGPASSFILE = Join-Path $env:LOCALAPPDATA 'LabBooking\PostgreSQL17\pgpass.conf'
if (-not $env:LAB_BOOKING_SECRET_KEY) {
    $env:LAB_BOOKING_SECRET_KEY = & $python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())'
    if ($LASTEXITCODE -ne 0) { throw 'Django 密钥生成失败' }
}
& $python -B -u manage.py runserver 127.0.0.1:8000 --noreload
```

登录页 `http://127.0.0.1:8000/login/`，管理员新增页 `http://127.0.0.1:8000/equipment/new/`。获准成员在本机受限目录 `%LOCALAPPDATA%\LabBooking\Protected\accounts.json` 查看对应角色的既有凭据，无访问权限时由负责保护清单的团队成员通过已批准私密渠道协助。新生成 Django 密钥会使旧会话失效，需保留会话时沿用原受保护的密钥。启动过程无需重复迁移或预置。
