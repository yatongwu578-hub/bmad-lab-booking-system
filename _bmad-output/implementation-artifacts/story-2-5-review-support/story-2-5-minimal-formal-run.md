## 1. 开窗前机器检查

1. 原 `.venv` Python 3.13.17、Django 5.2.19、PostgreSQL 17.12、实际 `runtime` 配置和 `lab_booking_app`。固定 `127.0.0.1:5433/lab_booking`、显式当前和会话角色、Read Committed、`public`，无 elevated 权限、无待迁移；不执行迁移。读取既有受保护 passfile、已存在三角色预置账密。主机只检查不改账号，确认管理员／教师／学生各一启用账号且业务角色精确，Django staff/superuser 不提供替代权限。不打印密码、哈希、会话或 CSRF 令牌。
2. 以实际运行角色执行同目录 `story-2-5-runtime-acl-readonly.sql` 的只读 ACL 检查，并将原始行、退出码、明确的有效／显式列权及差集存档。用限定别名的查询防歧义。NULL 或空 ACL 走 `CROSS JOIN LATERAL aclexplode(...)`，无行即无显式 ACL。另用当前源码的列清单复核既有 Equipment 锁权限、预约读取及 `status` 更新、历史 INSERT 和会话技术权限未变。不要用 `SELECT *` 做权限探针。
3. 若 AC-6 五列缺口仍在，仅在另行批准的窗口由有权角色补实测缺列，之后重复同一 ACL 脚本。历史上五列均缺，完整最小差集为下方语句。必须有十列 SELECT，`object_type`、`equipment_id` 仍不可读，不给表级 SELECT、转授或新写权限。不会对现有服务角色提权。若已精确匹配，不重复授权。

```sql

ON TABLE public.audit_operationhistory TO lab_booking_app;
```

4. 从单一独立只读观察会话按主键排序拍基线，记录 DB 实际时刻、预约、设备、历史及据时点计算的有效占用，读不到完整历史列时用获授权审计观察角色，不给运行角色临时宽权。每个查询范围独立算风险：全量纳入全部 pending，筛选只看目标设备 pending，详情只看该 ID。候选中有 `start_at <= clock_timestamp()` 或在本次窗口内将到点的 pending，就不访问该风险路径。查询前再次确认未越过窗口；占用的动态时钟自然变化与行写入分开核对。基线归档使用稳定列与排序，比较前统一数据类型，忽略观测时间差而非忽略实际业务字段。

## 2. 一次自动化取证

- 沿用仓库 `story-1-4-runtime-chrome.mjs` 的本地 Chrome CDP、原生表单和分角色新会话方法，以及 `run-story-2-3-demo-server.py` 独立日志与请求级 `connection.execute_wrapper` 写入守卫手法。不能直接重放旧 Story 脚本及其业务写分支。正式 2.5 驱动只准用真实本机 Chrome，固定同一 origin，真实 `GET /login/` 取 cookie 和表单 token，再原生提交登录表单并等待 302／身份页。新角色优先用独立 Chrome profile，或原生同源 logout 表单加 CSRF。不得手拼 POST、关闭 CSRF、复用陈旧 cookie 或为本地端口宽放 trusted origins。
- 正式预演限定已审核安全的 GET 查询。请求级 SQL 守卫阻断 equipment/reservations/audit 与未识别的 DML/DDL，也阻断账户权限、密码、启用状态等变化。仅允许会话所需的已知 `django_session` 技术写入，以及预置账户在该同源登录 POST 时既有的 `accounts_user.last_login` 单列更新（登录前核对密码哈希无需自动升级）。不需要新增登录元数据写权限。守卫允许已验证的设备行锁，不使用应用连接 DB `READ ONLY` 来代替守卫。独立观察会话始终只读。跨起始导致守卫拒绝时记录并停止，不把它当作正常空态。记录守卫判定和每条请求的无业务写证据。
- Chrome 记录真实文档请求方法、路径、状态、跳转、缓存头和 request ID。用 `Network.responseReceived`／`loadingFinished` 关联 `Network.getResponseBody`，必要时读取实际 DOM，输出正文散列、脱敏字段断言、必要截图。既有 Chrome 脚本是驱动参考，本 Story 需把正文和缓存头加入归档，不能声称旧脚本已采到。事件只提取白名单字段，不记录 Cookie、Authorization、POST body、CSRF 或原始 CDP 帧。完整正式申请人／原因数据只留受控本地，Git 仅放脱敏摘要与散列。
- 顺序在同一批次完成。匿名直访列表、筛选、详情应跳登录；学生和教师各登录后无管理入口，直访三路径均为 403，页面不含预约资料。管理员登录后由身份页点预约管理；若全量无写入风险，检查全量含历史、搜索表单与清除筛选；然后走实际筛选、选中既有预约详情、返回保留 `equipment`、回到身份页。找不到有效筛选记录则明确归档空态与安全详情。DOM 单独核对详情摘要字段及历史表，不用历史行中的同一字符串代替摘要。顺带核对缓存禁止和结果状态，无 Sprint 2 操作按钮。
- 用唯一新归档目录存 `stages.txt`、候选检查、源散列、运行角色 ACL、Chrome 请求／响应摘要、Django 日志和独立 DB 前后快照。按请求方法／路径／状态及唯一关联 ID 匹配，比较业务行与 ACL 前后散列；仅排除会话和获准的登录时间变化，不排除角色或账号启用状态。无记录不冒充浏览器实测。脚本只输出一次成功标记且原生进程退出 0 才算批次完成。交三位组员共同审阅，仅确认入口可发现、筛选／详情／返回是否顺畅、现场覆盖限制及验收结论，不填重复表。
