# Epic 2 Context: 预约申请、审核与个人管理闭环

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

让学生、教师能查询具体设备的占用、提交预约、查看自己的结果并按规则取消，让管理员能审核、取消并查阅处理历史。待审核申请到点后按需失效，既释放占用又保留历史，使预约流程可独立使用，避免重复占用和处理结果不透明。

## Stories

- Story 2.1: 提交具体设备预约并获得可靠申请结果
- Story 2.2: 查询具体设备在指定日期的占用时段
- Story 2.3: 查询本人全部预约及处理结果
- Story 2.4: 取消本人尚未开始的预约
- Story 2.5: 管理员查询预约详情并按设备筛选
- Story 2.6: 管理员批准待审核预约
- Story 2.7: 管理员拒绝待审核预约
- Story 2.8: 管理员取消预约并记录原因

## Requirements & Constraints

- 按具体设备与半开区间判定冲突，首尾相接不冲突，同一人可同时预约不同设备。申请成功立即待审核并占用，批准延续占用，拒绝、取消或失效释放占用。设备维修或停用禁止新申请和批准，不自动改变既有预约。不得编辑预约设备或时段、重开终态或物理删除历史。
- 北京时间起止均为整点，同一自然日内至少一小时，结束不晚于 23:00，开始严格晚于业务判定时刻，不另设预约窗口。到达开始时间仍待审核的记录只能失效，由授权查询、处理或冲突检查按需触发，不做后台扫描，已批准记录不适用。批准和拒绝仅在待审核记录开始前进行。本人只能在开始前取消自己的待审核或已批准记录。管理员取消待审核须在开始前，取消已批准须在结束前。管理员拒绝或取消须填写非空原因。
- 并发验收用真实 PostgreSQL 独立连接，在可用且无预存冲突的同一设备时段发起 20 个合法请求，连续 10 轮隔离数据，每轮恰好 1 成功、19 明确冲突、1 条有效占用，状态交错另组。标准竞争结论已有验收证据，核心机制不变且历史证据有效时复用，新交错单列实测。逐入口验证未授权请求被拒绝、无泄露、预约/设备/占用/历史均不变，实际未授权用例通过率须为 100%，合法对照单列。

## Technical Decisions

- `reservations` 统一处理预约，复用 `accounts`、`equipment` 和 `audit`。Django 业务服务先校验服务端角色、账号启用状态和归属并在锁后复核，申请人取会话账号，管理员不能申请。页面不直写，设备模块不反向调用预约模块。
- 短事务内先锁设备行，多设备按主键升序，锁后重读再以 PostgreSQL `clock_timestamp()` 采样一次 `t_decision`，复用于本事务所有业务时间判断。带时区时间点存储，按北京时间解释日期。Django 连接按既定决定显式使用 Read Committed，保留真实会话的隔离级别和锁后重读验证。
- 查询先授权，以稳定条件固定候选及设备，只锁有待审核候选的相关设备，纳入已结束但仍待审核的候选。锁后重读，不纳入并发新增，先收尾再按状态或是否结束筛选。无待审核候选不额外加锁，结果不承诺全库快照，提交仍须独立重查冲突。
- 从预约状态与区间推导占用，不另设占用表。实际转换追加历史并同事务提交，每条历史由数据库保证只关联一个有效对象，保留执行者、前后状态、适用原因和时间，系统失效不归为人工操作。合法失效后的业务拒绝仍提交失效及历史。确认数据库事务失败则整体回滚。数据库连接在提交阶段中断且无法确认持久化时，结果待核查，不臆断或自动重试。客户端断线本身不代表提交未知。

## UX & Interaction Patterns

- 设备日期查询区分占用与可申请时段，普通用户看不到他人详情，显示空闲不保证提交成功。本人记录同时显示预约状态和设备当前状态，在站内查看结果及适用原因。管理员可按设备筛选尚未结束的有效预约，处理后仍可查阅授权范围内的历史。

## Cross-Story Dependencies

- 全部复用 Epic 1 的身份、权限与设备目录。Epic 2 独立落实可用性检查、占用、失效和历史，不依赖 Epic 3。Epic 3 复用本 Epic 的筛选及人工处置能力。
- Epic 内前置关系为 2.2 ← 2.1，2.3 ← 2.1–2.2，2.4 ← 2.1–2.3，2.5 ← 2.1–2.2，2.6 ← 2.1、2.2、2.5，2.7 ← 2.1–2.3、2.5，2.8 ← 2.1、2.3、2.5、2.6。
