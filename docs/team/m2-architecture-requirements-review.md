# M2 架构需求审核记录

检查人：罗思婕  
检查日期：2026-11-05  
检查文件：ARCHITECTURE-SPINE.md  
编号说明：文件中的 AD-1～AD-8 对应 ADR-001～ADR-008。

| 编号 | 决定这么做 | 否决的备选 | 理由（回指需求） |
| --- | --- | --- | --- |
| ADR-001、ADR-002及功能映射表 | 保留学生和教师登录、查设备、查空闲时间、申请预约、查看结果、取消本人预约的功能。 | 暂未发现需要否决的方案。 | **用户功能检查后认为合理。** FR-001、FR-003～010均有对应安排；取消预约仍须满足本人、尚未开始等条件，不能任意取消。 |
| ADR-002、ADR-006 | 管理员通过专门页面批准、拒绝和取消预约，并维护设备的维修、停用及恢复状态。 | 设备维修或停用时，直接自动取消全部已有预约。 | **管理员主要功能齐全。** 对应FR-011～017，故障后的已有预约由管理员人工处理。建议明确按设备查找受影响预约的入口，避免漏处理。 |
| ADR-002、ADR-005 | 学生和教师只能查看自己的预约详情；查看他人占用情况时只显示时间区间。审核、取消他人预约和维护设备由管理员操作。 | 学生查看他人私人预约记录，或通过直接访问页面执行管理员操作。 | **权限检查后认为合理。** 符合FR-002和NFR-002，既能查询设备空闲情况，又保护他人的个人信息。管理员身份也不能绕过业务规则。 |
| ADR-004、ADR-005、ADR-006 | 到开始时间仍待审核的预约，在相关查询或业务操作触发时转为已失效；已批准预约不受此失效规则影响。 | 把已批准预约一起失效，或把没有定时任务的方案描述成“到点立即更新”。 | **状态区分合理，但需要说明更新时间。** 本稿对应FR-018，采用访问时触发更新。建议明确提示“到时后首次相关访问时更新”，避免用户误解。 |
| ADR-001、ADR-006及FR-018映射 | 保持基本预约管理范围，不增加自动候补、微信通知或故障自动取消。新增失效规则须核对最新版PRD。 | 未确认需求便加入扩展功能，或直接认定FR-018已经获得小组同意。 | **未发现上述多余扩展功能，基本功能也有对应安排。** 但此前10月30日PRD明确不做自动过期释放，本稿新增了FR-018。应确认最新版PRD是否已接受该变更，再统一需求与架构。 |
| ADR-002及Deferred | 采用明确的账户角色分工和管理员专门页面，不使用Django Admin直接修改预约、设备和历史记录。 | 通过后台直接改状态，绕过审核条件、取消原因和历史记录要求。 | **这些AI建议从使用角度看合理。** 用户与管理员各有操作入口，预约处理遵守相同规则，符合FR-002、FR-012～017。具体模块划分等待审建议仍需小组确认。 |
