# Sprint规划业务审核意见

- 检查人：罗思婕
- 检查日期：2026-11-19
- 检查文件：sprint-plan.md、sprint-planning-review.md
- 审核范围：普通使用者的功能、操作流程及两轮工作划分

| 检查问题 | 审核意见及理由 | 建议 |
| --- | --- | --- |
| 1. Sprint 1能否形成基本可用的功能？ | **可以形成初步可用的申请与查询功能，但不能完成完整预约流程。** 学生和教师能够登录、查看设备及占用时间、提交申请、查看本人记录；管理员能够查询申请。但此时不能批准、拒绝或取消，新申请通常只能保持待审核，或到时按规则失效，不能凭申请成功就使用设备。 | 接受其作为第一轮演示增量。演示时明确说明“申请已提交，审核和取消将在Sprint 2提供”，不能宣称已经可以完整办理预约。 |
| 2. Sprint 2再做审批、取消、停用和维修，顺序是否合理？ | **整体合理。** 先有账号、设备、申请和查询，后续审核与取消才有操作对象。设备维修停用放在最后，可以复用管理员筛选、取消和本人结果查询，完成故障人工处置。代价是Sprint 1期间用户无法撤回误提交的申请。 | 保留当前顺序，但Sprint 1宜作为受控演示阶段。若计划让真实用户提前使用，应优先讨论是否将2.4本人取消前移，并重新核定工作量。 |
| 3. 业务功能有没有遗漏或多做？ | 两轮合计覆盖全部13条Story：师生登录、查设备、查占用、申请、查结果及本人取消；管理员新增和维护设备、查询、批准、拒绝、取消及维修停用恢复。**未发现主要功能整项遗漏或明显多做。** 计划也明确不增加自动候补、微信通知、故障自动取消、处罚或后台扫描。 | S1必须按计划交付权限、冲突检查和按需失效，不能等S2再补。S2维修停用后应保留已批准预约，由管理员筛选并人工处理，同时让申请人看到设备当前状态。 |
| 4. 哪些功能必须先完成？ | 1.1登录及角色识别先于受保护操作；1.2设备档案先于设备查询和预约；2.1申请及时间、冲突、失效和历史机制先于后续预约操作；2.3本人查询先于2.4本人取消；2.5管理员查询先于2.6批准、2.7拒绝和2.8管理员取消。按当前正式依赖，2.8还须等待2.6，3.1须等待此前全部Story。 | 继续遵守计划中的依赖。2.6和2.7互不依赖，可以分别开展，但前提是各自的S1基础已经实际完成。测试用的批准、拒绝等记录不能变成提前开放的S2业务入口。 |
| 5. 8条与5条的工作划分是否合理？ | **从用户功能和依赖看，没有明显不合理，但不能仅按条数判断工作量均衡。** S1虽然8条，却包含环境、账号、设备和预约基础，以及2.1完整并发验收；S2虽只有5条，还包含实验、跨功能回归、故障处置及最终交付，工作量也不轻。当前缺少可用工时和实际估算，无法确认能否按期完成。 | 启动前确认日期和可用工时，重点估算2.1及S2实验与综合验收。若需调整2.3或2.5，必须先满足S2实验和审核功能的前置条件，不能为减少S1工作量而删减验收要求。 |

审核结论：从业务角度接受当前8条／5条的两轮划分建议，前提是明确Sprint 1仅完成申请与查询增量，Sprint 2才完成完整管理闭环；启动前仍需负责人确认容量、日期和相关准备事项。
