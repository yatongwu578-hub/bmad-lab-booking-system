| **ADR-003 / ADR-008** | **重复预约：有条件保证只有1个成功。** 所有申请、审批、取消和失效路径先锁同一设备行，锁后重读、检查有效占用、写入预约和历史，并持锁至提交。20个同设备请求形成1个成功、19个明确冲突。直接SQL或绕过统一业务入口的写入不受此保证。 | 先查“是否可用”再写入；首版只依赖数据库排斥约束；不设置并发保护。 | 先查后写会让多个请求同时通过检查并产生重叠占用，违反FR-007、FR-008和NFR-001。ADR-003负责设备行锁协议，ADR-008负责真实PostgreSQL并发验证。 |
| **ADR-004** | **时间边界：达到开始时间后不会批准。** 锁后重读再采样一次 `t_decision`；`t_decision >= 开始时间` 时只能转为已失效，只有严格早于开始时间才允许批准。判定在开始前完成、提交跨过开始时间时，批准仍有效。 | 请求到达时间；事务开始或提交时间；页面时间；线程偶然命中整点。 | 锁等待可能跨越开始或结束边界，必须使用统一业务判定时刻。对应FR-006、FR-012、FR-018和T-02。相等边界采用“大于或等于即失效”。 |
| **ADR-003 / ADR-004** | **取消与批准并发：不会产生非法最终状态。** 两个操作共用设备锁。取消先提交，则批准因状态已终止而失败；批准先提交，则后续取消仍须满足本人、尚未开始或管理员、尚未结束等条件。状态与历史同事务提交。 | 按页面旧状态直接覆盖；两个操作各自检查后独立提交；取消和批准使用不同锁。 | 旧状态覆盖会丢失已发生的取消，违反FR-008、FR-010、FR-012、FR-014和NFR-001。锁后重读使结果等价于某个串行顺序。 |
| **ADR-003 / ADR-006** | **设备停用：已有预约保留，新申请和批准被禁止。** 设备状态与预约状态分开；维修或停用后，新申请和待审核批准按设备不可用拒绝。既有待审核、已批准预约不自动取消或失效，显示设备当前状态并由管理员人工处理；恢复不复活终态记录。 | 设备停用后自动取消或失效全部预约；只改设备状态而允许旧页面继续批准；删除受影响预约。 | 对应FR-009、FR-014、FR-017和FR-018。该设计既阻止新增占用，也避免未经授权的故障自动取消和数据丢失。 |
| **ADR-005 / ADR-006** | **失效与历史：记录原因，重复访问不重复写记录。** 授权查询、审核、取消或冲突判断中锁设备并重读；只有仍为待审核且已到开始时间时才转为已失效。历史追加系统执行者、固定原因、前后状态、`t_decision`和记录时间，并与状态变更同事务提交。 | 只在页面虚拟显示失效；周期后台扫描；只保存最后原因；每次查询无条件追加失效历史。 | 对应FR-015和FR-018。同一设备上的并发检查被锁串行化，后到请求看到已失效后不再转换，因此避免重复失效记录；状态、占用和历史保持一致。 |
| **ADR-002 / ADR-005 / ADR-008** | **权限测试：未登录、越权和非法审批可被拒绝，且不错误修改数据。** 所有入口先验证会话、角色和归属，再执行锁和写入；申请人取当前登录账号；管理员不能申请，普通用户不能审核或维护。未授权用例同时核验拒绝、无受限详情泄露、预约占用及业务历史不变。Admin URL具体关闭方式仍须在实现前落实。 | 只隐藏页面按钮；依赖前端权限；信任表单申请人；Django Admin直接编辑业务模型；先执行失效写入再判断越权。 | 对应FR-001、FR-002和NFR-002。权限检查必须早于任何失效副作用，否则越权请求可能错误修改他人数据。 |
| **ADR-008** | **测试可实施：设计依据齐全，但尚未形成可执行测试，也未通过。** NFR-001采用真实PostgreSQL、独立连接、统一启动屏障、20请求×10轮、每轮隔离数据，断言1个成功和19个冲突。NFR-002以权限矩阵列出的未授权用例总数为分母，每例检查拒绝、无泄露、无业务及历史变化，合法对照单列。T-01～T-04均已绑定对应验证节点。 | SQLite替代PostgreSQL；20个请求复用同一连接；只模拟时间证明锁行为；随机并发代替固定交错用例；把设计文档或全部拒绝当作测试通过。 | 对应课程第4、13节及NFR-001、NFR-002。T-01固定交错场景、T-02负责时间取证、T-03负责成对权限案例、T-04隔离稳定竞争夹具。当前仍需将T-01、T-03、T-04细化成具体用例表、路由清单和测试夹具。 |
