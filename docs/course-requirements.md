>
> **更新记录**：2026-10-23 初版（根据课程 PPT 和老师最新通知整理；未自行新增评分门槛）。

## 0. 使用方式和基本原则

1. **每次进入新的 BMAD 工作流前先读取本文件**；AI 只协助分析和执行，不得默认知道课程 PPT。
2. 将本文件列为 Codex 仓库根目录 `AGENTS.md` 的必读材料，同时从 `README.md` 链接本文件。
3. 本文件的**课程硬性要求**不得因 BMAD 默认工作流允许裁剪而被省略。实际 BMAD 命令名称以项目安装的课程兼容版本和 `bmad-help` 为准。
4. 所有事实性证据必须来自**实际**讨论、会话、代码、Git、测试及老师正式下发的变更；**不得虚构**需求访谈、AI 建议、人类否决、度量、变更任务、提交记录或验收结果。
5. **事实与建议分离**：本文件中标注“【课程硬性】”“【课程评分】”“【老师新通知】”的内容源于指定材料；标注“【团队建议】”“【待老师确认】”的内容不等于老师额外要求。
6. 当前为 **3 人小组**，已有 **1 个 ChatGPT Plus（可使用 Codex）**。这两点是团队现状，不是新的课程评分约束；正式成员、职责和实际工具版本由小组填写。

## 2. 选题硬性门槛【PPT 第32页】

> **不满足选题硬性门槛：不予评分。**以下全部为【课程硬性】。

- [ ] 选题为**真实可用的小系统**，且有明确的真实使用者。
- [ ] 可合理拆为**至少 3 个 Epic** 和 **至少 12 个 Story**。
- [ ] 至少 **2 条可测量的 NFR**，可以是性能、并发、安全、可运维性等。
- [ ] 至少 **1 个具有并发或数据一致性风险的功能点**，能支撑真正的架构取舍。
- [ ] 技术栈自由选择，但**必须在评审机器上依照 README 能够启动**。

**PPT 明确不接受**：纯静态页面、纯爬虫脚本、算法题集合、把现成开源项目换皮改名。

**选题登记**：第 1 周周三前由组长完成登记。【PPT 第32、38页】

### 当前候选选题【团队建议】

- 名称：实验室设备预约管理系统。
- 真实用户、痛点、业务边界、三大 Epic 和 NFR 目标值必须由小组核验，不能由 AI 臆造。
- 可能的一致性风险：同一设备同一时间窗口发生并发预约冲突；需要在 PRD 中精确定义何为冲突及验收方法。

## 3. BMAD 四阶段与顺序【PPT 第10–15、21、26页】

1. **分析（Analysis）**：产品问题、用户、目标、成功度量和范围；形成 `product-brief.md`。
2. **规划（Planning）**：形成编号 FR 与可测量 NFR 的 `PRD.md`。
3. **方案设计（Solutioning）**：先架构及 ADR，再创建 Epic 和 Story，形成 `project-context.md`，通过就绪门禁，初始化 Sprint 计划。
4. **实施（Implementation）**：按 Story 迭代开发和评审，更新 Sprint 状态；处理变更、执行回顾、整理测试和最终证据。

**不可打乱的重要顺序**：按照本讲义 v6 方法，**架构在史诗与故事创建之前**。【PPT 第10页】

**流程纪律**：【PPT 第21、39页】每个独立 BMAD 工作流使用一个新的 AI 会话，减少上下文串扰；不能一条会话从头完成全部工作流；不能跳过架构直接开发。工具的正式命令名称以当前实际安装版本显示为准。

**规划档位**：【PPT 第12页】选择并说明过程裁剪档位与理由；但本次课程指定产物全部必交，不能用“轻量档位”为由跳过 PRD、架构、ADR 或故事卡。以适合本次作业的完整产物链为准。

**Story 验收标准**：【PPT 第14页】不能只写“功能正常”；必须具体、可自动验证，能映射到测试断言。故事按 `draft → ready → in-progress → review → done` 等真实生命周期演进。状态名称以实际 BMAD 配置为准，严禁伪造状态历史。

**就绪门禁**：【PPT 第26页】必须检查 FR、NFR、ADR 与故事的一致性，有重大冲突时先修正，不允许带着明显矛盾继续开发。

### 4.1 FR 到 Test 的可追溯性【PPT 第11、23–26、37页】

- 需求必须编号（如 `FR-001`），便于后续追溯。
- 至少能够展示：**FR → ADR / 架构约束 → Story / 验收标准 → Test / 运行证据** 的完整链路。
- 第 37 页明确：老师抽查 **2 条 FR**，检验链条是否贯通。
- 需求与架构或故事发生变更时，必须同步更新依赖文档。

### 4.2 决策日志结构【PPT 第36页】

每条必须包含以下证据维度：

1. **触发**：具体工作流、会话或评审位置。
2. **AI 建议**：实际建议了什么及理由，最好保留可追溯的原始会话位置。
3. **人类判断与依据**：接受 / 否决 / 实质修改，回指相关 FR / NFR / ADR，不能只写“我们觉得”。
4. **结果**：实际变更了哪些文件、故事、架构或代码，可附 commit / PR。
5. **事后验证**：后续证据是否证明判断奏效，或暴露后续问题。

**禁止凑数**：“AI 建议 React，我们同意了”且没有依据、备选和验证，不是高质量记录；“至少 5 条否决/修改”也不能编造。

## 5. 必做实验 A：规划深度对照【PPT 第34页；度量模板第29页】

**目标**：不是预设 BMAD 更好，而是用数据检验完整规划对软件交付的净效益。【课程硬性】

### 分组与控制

- **故事 X（实验组）**：完整路径，提供 PRD、架构与 ADR、`project-context.md`、故事卡，使用 `bmad-build`。
- **故事 Y（对照组）**：开始一个全新干净会话，**只描述一句功能需求**；不给 X 的 PRD / ADR 等规划产物，也不能人为泄漏这些上下文。
- X 和 Y 必须**难度相当**，必须写出为何判断难度相当。
- 两组在**同一个人、同一天、同一宿主、同一模型**的条件下进行。
- Y 完成后与 X 采用**完全相同的 `code-review` 标准**评审。
- 不可刻意降低 Y 组的 AI 能力或审查力度以获得“规划更好”的结论。
- 保存 X、Y 的真实输入、会话日志、完成产物、审查结果、测试与指标。

### 五项必需度量【PPT 第29页】

| 度量项 | X 数值 | Y 数值 | 采集方法/证据 |
| --- | --- | --- | --- |
| 平均每故事会话轮数 | 待测 | 待测 | 记录从开始到完成的实际对话轮数。 |
| 代码评审首轮通过率 | 待测 | 待测 | 第一次 `code-review` 是否无须修订。 |
| 违反 `project-context` 规则次数 | 待测 | 待测 | 同一规则表下审查实际命中次数。 |
| 与 ADR 冲突的实现次数 | 待测 | 待测 | 审查/集成时发现的架构偏差。 |
| 返工故事数 | 待测 | 待测 | 标为 done 后因问题重新修改的故事数。 |

> 数据必须真实。对于只有一个故事的组，比例或平均值的分母必须明确，绝不能补造“样本量”或“团队整体统计”。

### 报告必须回答的 3 个问题【PPT 第34页】

1. 两条路径的五项指标差多少？
2. 差异主要来自需求、架构还是上下文？
3. 把差异乘以 12 个故事后，本组规划投入是否值得？

### 结果与局限

- 若实验显示“完整规划的净收益为负”，但证据真实、推理合理，也属于有效结果。
- 样本仅 2 个故事、无随机化，**必须主动陈述实验局限**（PPT 第34页讲师备注）；不能宣称普遍证明 BMAD 更优。

## 6. 必做实验 B：第 3 周变更注入【PPT 第35页】

**触发**：第 **3 周周一上午**，老师给每组下发一条**不同的需求变更**；**当天 18:00 前提交影响分析**，变更本身的实现置于第 2 个 Sprint。【课程硬性】

**规定动作（四步，顺序不得乱）**：

1. 调用 `bmad-correct-course` 对真实下发的需求变更做影响分析，**不能直接改代码**。
2. 产出影响分析表：受影响 FR / NFR / ADR / Story 清单；架构是否需要改；预计工作量。
3. 人工进行范围取舍，并在 `decision-log.md` 写清 **新增什么、延后什么、砍掉什么、理由是什么**。
4. 在第二个 Sprint 中实现接受的变更，同步更新相关产物与测试。

**评分关注**：影响分析完整、诚实；取舍根据需求优先级与剩余工期，有理有据；**合理拒绝部分变更并说明理由也是有效答案**。不能一律拒绝，也不必一味答应全部实现。

**重要禁止**：老师未正式下发变更前，不得伪造“已收到的变更”或预写实验结论。

## 8. 评分规则【PPT 第37页】

| 维度 | 分值 | 关键评分依据 |
| --- | ---: | --- |
| 人机决策日志 | **25** | 批判性介入是否有凭证；否决的质量重于数量。 |
| 规划产物的可追溯性 | **20** | 抽查 2 条 FR：`FR → ADR → Story → Test` 能否走通。 |
| 实现与质量 | **20** | 按 README 可运行；每条 NFR 有测试证据；评审形成闭环。 |
| 工作拆分与敏捷执行 | **15** | Story 粒度、可验证的验收标准、真实的冲刺状态流转。 |
| 两个必做实验 | **15** | 实验 A 测量真实且有结论；实验 B 影响分析完整。 |
| 演示与团队协作 | **5** | Git 贡献分布可见；演示讲清取舍，不是只演功能。 |
| **总分** | **100** | 课程作业占总成绩 30%。 |
| 可选加分 | **最多 +5** | 用 **bmb** 模块自定义工作流或智能体，说明动机和实际效果。 |

**分值理解**：决策日志（25）+ 两实验（15）= 40 分，超过实现与质量（20）；核心考察管理和判断，但**不免除**可运行软件、NFR 与代码评审要求。

## 9. 红线、扣分风险与禁忌【PPT 第32、34–36、39页】

### 9.1 PPT 明确写出的红线 / 后果

- **选题未满足第 2 节门槛** → **不予评分**。【PPT 第32页】
- 文档与代码不一致（例如只改代码不改需求/文档）→ **发现即扣分**。【PPT 第39页】
- `decision-log.md` 全篇都是“同意 AI 方案”、无真正判断 → **该项严重失分**；PPT 红线将其列为发现即扣分。【PPT 第36、39页】
- Git 历史只有一两次大提交，不能体现真实演进 → **发现即扣分**。【PPT 第39页】
- 未提交 AI 使用声明 → **发现即扣分**；**隐瞒使用 AI → 按学术不端处理**。【PPT 第39页】

### 9.2 其他必须规避的过程性失误

- 把 PRD 写成空泛文书，后续从不回指它。【PPT 第39页】
- 所有工作流都堆在同一个会话里，导致上下文污染。【PPT 第39页】
- 跳过架构，直接拆故事并开发；并行时才发现冲突。【PPT 第13、39页】
- 故事验收标准只写“功能正常”，无法转成自动化测试。【PPT 第14、39页】
- 所有 Story 一次性从 draft 跳到 done，缺乏真实敏捷过程证据；PPT 提示该项将按最低分计。【PPT 第39页】
- 在实验 A 中故意弱化 Y 组或夸大样本推论。【PPT 第34页】
- 在实验 B 中先改代码后补影响分析。【PPT 第35页】
- 假造 AI 对话、实验指标、人工决策、需求变更、提交历史或测试结果。【真实性原则；不得将虚构材料冒充证据】

> PPT 没有逐一规定每条红线固定扣多少分，**不要擅自编写统一扣分数字**。

## 10. 可选内容与提高表现的方式【PPT 第17、37、40页】

### 10.1 明确的可选加分

## 13. 每阶段进入/退出核对单【团队建议，检查项对应课程要求】

### M0：启动前准备

- [ ] 确认真实题目、真实使用者与并发/一致性风险点。
- [ ] 建立**唯一 GitHub 仓库**，邀请 3 人协作。
- [ ] 放入 `docs/course-requirements.md` 和根目录 `AGENTS.md`。
- [ ] 在 README 链接本文件并记录课程信息和实际工具版本。
- [ ] 确认 BMAD 可用，用 `bmad-help` 选择 Analysis 工作流。

### M1：分析和需求基线

- [ ] 周三前完成选题登记。
- [ ] 产品简报写清用户、问题、成功指标和非目标。
- [ ] PRD 的 FR 编号、NFR 可测、范围明晰，覆盖后续 3 Epic / 12 Story 规模。
- [ ] 保留真实评审证据、AI 交互与关键人工决策。
- [ ] M1 门禁检查通过后才进行下一阶段。

### M2：架构、故事与就绪

- [ ] 先完成至少 5 条 ADR 和备选方案否决理由。
- [ ] 再生成至少 3 Epic、12 Story，可自动验证每条验收标准。
- [ ] 至少 8 条有约束力的 `project-context.md` 规则。
- [ ] 执行就绪门禁、修复冲突，生成 `sprint-status.yaml`。
- [ ] 完成 M2 门禁，并可演示 FR 到 Story 及 Test 的链路。

### M3：冲刺 1 与变更注入

- [ ] 真实推进 Sprint 1 Story 状态、评审与测试。
- [ ] 接到老师第 3 周周一变更后，先运行 `bmad-correct-course`。
- [ ] **当天 18:00 前**提交完整影响分析（不预造内容）。
- [ ] 做真实的新增 / 延后 / 砍掉取舍并记录。
- [ ] 展示核心史诗可运行的 Demo。

### M4：冲刺 2、实验和封存

- [ ] 实现被接受变更及合理范围内剩余故事。
- [ ] 完成实验 A 两故事对照及 5 项真实度量、3 个讨论问题和局限说明。
- [ ] 完成实验 B 实际结果复盘；更新 `retrospective.md`。
- [ ] 决策记录不少于 15 条、真实否决/实质修改不少于 5 条。
- [ ] 每条 NFR 都有测试证据、README 可复现启动。
- [ ] AI 使用声明完整、演示录屏约 10 分钟，演示取舍而不仅是功能。
- [ ] 所有必需文件进唯一 GitHub 仓库，保存里程碑和最终提交状态。
